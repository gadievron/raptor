# Reporting engine

`core/reporting` builds deterministic reports and operator summaries without LLM
calls. Existing `ReportSpec`, `render_report`, and formatting APIs remain available.
New callers use `ReportContext`, typed `Block` content, and `ReportDocument`.

## Operator output

Standalone scan and CodeQL completion capture final SARIF as Unconfirmed findings.
Scanner levels are kept separate from security severity and verdicts. Findings
have snapshot-scoped display references that resolve through the captured document.
The quick view includes tool outcomes, counts, a bounded finding list, limitations,
and a validation suggestion when appropriate. Full report failure does not remove
available results from the screen. Suppressed findings remain in captured data;
the scan quick view honors `--show-suppressed`.

`summary.json` and chat-ready `summary.md` are independent of full report files.
Validation keeps `summary.txt` for existing consumers. Claude command instructions
display the mechanical summary; they do not ask an LLM to reconstruct counts or
edit saved reports. Python callers can supply a stream to `complete_reporting` or
consume the structured result without printing.

## Formats and options

Scan, CodeQL, agentic, project report, SCA scan (both entry points) and rerendering, web,
fuzzing results, OpenAnt, audit run/resume/report, engagement report, describe,
and binary report accept these controls at their reporting boundary:

- `--report-format markdown|json|html|xml`, repeatable for multiple formats.
- `--report-output PATH`, a matching-extension filename for one format or a directory.
- `--no-report`, keeping the quick summary and scanner evidence.

Direct validation callers can pass `ReportOptions` to `PipelineConfig`,
`run_validation`, or `write_validation_report`. The validation helper's final
stage also accepts the common report flags.
Existing project compatibility exports remain generated by `/project report`;
`--no-report` controls the additional consolidated report rather than removing
established finding/annotation exports.

Describe requires an explicit `--report-output` and keeps its default read-only
stdout behavior. Binary `report` keeps its existing Markdown display by default;
explicit controls export captured investigation/map JSON without analysis. Audit
and engagement generate their detailed reports through portable domain builders.
Their established Markdown and JSON companion filenames remain the defaults;
explicit formats select the detailed exports. Canonical domain JSON remains owned
by each domain and is never replaced by a rendered report document. SCA `--html` adds HTML to requested
formats. Corpus preparation rejects fuzz-result reporting flags. Existing machine
JSON/stdout modes remain separate from human summaries.

Markdown is the default full report. HTML is static escaped content without script
or remote assets. Explicit legacy Markdown sections display as labeled literal
content in Markdown and HTML, with format diagnostics. A snapshot digest never
authorizes active imported Markdown. XML represents RAPTOR's report schema;
it does not claim compatibility with SARIF or an external XML standard. PDF is not
advertised or silently installed; another explicit renderer can be registered via
`register_renderer(Renderer(...))`.

## SBOM reports

SBOM commands keep their native inventories, CSV/JSONL exports, notice bytes,
and upgrade evidence. A short operator summary appears on stderr so JSON and CSV
stdout remain usable in pipelines. An inventory is not a vulnerability assessment;
missing declarations, unknown coverage and unverified notice evidence remain explicit.

When a command creates an output directory, its additional reports are stored in
`report/` inside it. For commands that normally only print results or save a JSON
file, choose a report destination explicitly. For example:

```bash
raptor-sca sbom inspect release.cdx.json --out inventory
raptor-sca sbom diff old/inventory.json inventory/inventory.json --report-output changes
raptor-sca sbom stats inventory/inventory.json --report-format xml --report-output statistics
```

SBOM reports currently support Markdown, JSON and XML. Native JSON remains the
full domain evidence; the report JSON describes the presentation. Large inventories
use a declared bounded report capture while native exports retain the full selection.
Use `--help` for output controls, selection and display options.

To regenerate a saved report without reopening the SBOM, accessing the network,
or rechecking advisories or notice bytes:

```bash
python -m core.reporting render inventory/report --format xml --output inventory-report.xml
```

SCA scan reports also capture metadata from the SBOM they emit. Project reports
show available committed SBOM captures per selected run/output, including source
fingerprints, unresolved declarations and notice-verification status. Counts remain
separate for each inventory. A project baseline comparison records which evidence
captures changed or left the selection; it does not infer component remediation.
Legacy runs without a committed capture are not silently reconstructed from live SBOMs.

Inventory diffs use the SBOM comparison rules, including explicit ambiguous matches.
A package disappearing from an inventory is not proof that a vulnerability was fixed.
Upgrade verification still requires the domain's recorded advisory coverage.

## Programmatic completion

```python
from pathlib import Path
from core.reporting.adapters import context_from_sarif
from core.reporting.document import StageEnvelope
from core.reporting.options import ReportOptions
from core.reporting.service import complete_reporting

context = context_from_sarif(
    [Path("out/combined.sarif")],
    target="src", run_id="scan-1",
    stages=[StageEnvelope("semgrep", "completed")],
)
result = complete_reporting(
    context, Path("out"), stem="scan-report",
    options=ReportOptions(formats=("markdown", "html")),
)
```

For native workflows, adapt findings with `native_findings`, build a `ReportContext`,
and supply stage envelopes, scope, artifact references, diagnostics, and namespaced
extensions. An in-process stage returns typed values; a subprocess may serialize
the same envelope. The orchestrator owns reporting capture, not a new file per
stage. Existing workflow evidence/state schemas are not replaced.

`core.reporting.results.NativeResult` captures native JSON, optional findings,
explicit metrics, stage envelopes, artifact references, and portable blocks.
`complete_native_result` supplies the common completion boundary. Omit the finding
population for inspection results: an inventory is not a zero-vulnerability
assessment. Domain adapters redact secrets before capture; web applies its existing
artifact redactor.

Do not pass credentials, raw environments, arbitrary Python objects, or non-finite
numbers. Serialization rejects unsupported values rather than stringifying them.
Context and document versions are checked on load; unknown required fields are
rejected. Use namespaced extensions for optional domain data.

## Persistence and regeneration

A report generation lives under `.reporting/<generation>/`. It captures
`report-context.json`, `report-document.json`, rendered files, and a manifest.
`reporting-manifest.json` identifies the committed generation; root-level files are
compatibility mirrors, not a transactional multi-file bundle. Prior generations
remain available. `expected_generation` provides an optimistic publication guard
for callers whose selection must remain pinned; publication itself is file-locked.
Input SARIF digests come from the same guarded read as parsing.

Offline commands require neither analysis tools nor an LLM:

```bash
python -m core.reporting capabilities
python -m core.reporting sarif out/combined.sarif --out out/triage
python -m core.reporting render out/report-document.json --format html --output report.html
python -m core.reporting delta baseline/report-context.json candidate/report-context.json --out delta
python -m core.reporting native workflow.json --findings-key results --out native-report
python -m core.reporting native inventory.json --findings-key - --out inventory-report
python -m core.reporting native workflow.json --out pass-report --run-id R --pass-id validation --attempt-id 2 --parent SNAPSHOT_ID
```

Native imports default to Unconfirmed; `--recorded-verdicts` explicitly displays
source claims with imported provenance. An artifact digest proves byte identity,
not trust or validation. Rendering opens captured input JSON only; artifact URIs
and original paths never trigger source reads or network requests.

Native imports retain workflow JSON metadata outside the finding array. Render
and delta also accept committed output directories: readers verify immutable
context/document hashes and ignore stale compatibility mirrors. Generation identity
includes filenames and renderer versions; external destinations never modify an
immutable manifest. Markdown declares presentation truncation while preserving
full values in the captured document.

Capture currently limits individual SARIF reads through the existing guarded
loader, aggregate input to 128 MiB, report findings to 10,000, and serialized/rendered
documents to 32 MiB. SARIF truncation and invalid inputs are declared. Native
captures above the complete-capture limit are rejected. The quick view caps rows,
stages, and diagnostics while preserving totals. Values omitted by capture are not
described as validated or complete.

## Project views and deltas

Project code continues to select/merge native findings using existing local/imported
origin precedence, status rank, recency, and provenance union. The consolidated
report captures that selection, annotations, re-adjudication records, dependency
findings, and available run snapshot IDs. Historical runs without reporting
envelopes retain unknown stage completeness. Project export stages a replacement
before swapping directories and preserves unrelated files. Running runs are
excluded from final views with an explicit limitation. New standalone scanner
snapshots supply findings when canonical native findings files are absent. Run
merges preserve immutable source report histories in `report-histories/`, including
provenance, rather than discarding hidden generations.

`/project report --baseline PATH` compares an explicit context snapshot with the
new project view. Delta matching uses exact occurrence references or an explicit
caller-provided lineage map. Absence is never a fix, disproof, or resolution.
Unknown/different scopes and partial inputs are declared. `delta --lineage FILE`
accepts a bounded explicit mapping; ambiguous splits never also imply absence.
Evidence, stage/coverage, policy, annotation, and selection changes are separate
from newly observed findings.

### Lifecycle and observation lineage

The run lifecycle owns `reporting_identity` in `.raptor-run.json`: a schema
version, run/pass/attempt IDs, and segment number. Fresh executions get fresh IDs.
Reentrant starts retain the active attempt. Resume retains its run/pass/attempt,
increments the segment and pins the preceding committed reporting generation.
Legacy runs acquire an identity on resume with prior lineage explicitly unknown.
Direct Python reporting without a matching lifecycle records unknown lineage;
it does not create or alter a run lifecycle.

`libexec/raptor-run-lifecycle start ... --retry-of RUN_DIR` explicitly starts a
new attempt of a failed, interrupted or cancelled run of the same command and
compatible target. It shares the recorded pass ID when available. This does not
declare supersession, comparable coverage or issue resolution. Repeating that
bootstrap retains the attempt; changing an active attempt's retry relationship
is rejected. `--parent-run RUN_DIR` records a workflow relationship (including
agentic child passes) without sharing child pass IDs or attesting findings.
A new execution may name its predecessor in the same directory; an active
execution cannot name itself as parent.

Scan, CodeQL, validation and agentic captures carry these IDs into their stage
envelopes and occurrence references. Validation imports link observations only
when the selected input matches an adjacent committed capture's exact canonical
content and recorded occurrence. Native import markers supplied in the input
are discarded and rebuilt from that capture. `reporting-input.json` records the
selected subset, pinned source generation and owning attempt; stale markers
from another attempt are ignored, and fresh inventory invocations clear prior
selection markers. Resume links require an unambiguous producer
ID and matching location/type within the same attempt. None of these hashes or
IDs authenticate imported evidence or replace domain provenance gates.

Delta uses recorded input/resume lineage only when it names the explicitly
chosen baseline snapshot. An explicit `--lineage` map overrides automatic
selection. Conflicting parents and multiple candidates consuming one baseline
observation remain uncertain; no verdict comparison is inferred.

Project reporting freezes findings from committed captures, falling back to
domain files for legacy runs. A capture belonging to an earlier lifecycle is
excluded with a diagnostic; it cannot be attributed to a new execution whose
report publication failed. It uses recorded relationships to group scan and
validation observations before applying the existing origin/status/recency
policy. Exact duplicate local captures do not add a population; imported claims
cannot create local lineage links. Historical predecessors explicitly pinned
inside a selected local directory are retained, so a later targeted pass cannot
silently remove unselected scan observations. At most 32 predecessors are read
per selected directory, with missing/inconsistent or limited history declared.
Local predecessor references remain usable when the output directory is moved.
There is no directory crawl or automatic read of unselected external parents.
Historical snapshots are identified separately from physical run counts, and
stage coverage remains separate rather than being summed across passes.

## Diagrams

`packages/diagram/reporting.py` adapts existing bounded generators to captured
inputs and typed diagram blocks. Agentic and validation embed captured finding
charts and capture existing context/path/graph diagrams through an explicit generator
adapter into typed blocks; `diagrams.md` is derived from the same document. Markdown uses a conservative
Mermaid subset. Static HTML retains textual equivalents when no safe visual backend
is available. Diagram rendering never changes finding counts, fetches assets, or
reruns analysis.

## Migration census

| Command boundary | Integration and remaining compatibility work |
|---|---|
| Scan; both CodeQL entry points | Final SARIF adapter, summary, portable reports, early failures |
| Validation, disk and native orchestrator | Common capture/writer, stage envelopes, portable enrichment and separate unverified groups |
| Agentic | Common capture/writer, portable phase enrichment, outcomes and captured diagrams |
| Project report | Frozen selection, merge decisions, annotations, native exports, optional explicit baseline |
| SCA scan and render | One portable domain builder for MD/HTML/JSON/XML; KEV, EPSS, reachability, licenses, health and evidence |
| Web | Redacted native capture, verification state, partial/empty outcomes |
| Fuzz result | Native result with crash metrics; no fabricated vulnerability population |
| OpenAnt | Normal, forecast, skipped, interrupted results; primary findings separate from recovered hints |
| Audit run/resume/report | Portable detailed reports, completeness/residue, grouped findings and evidence; canonical JSON retained |
| Engagement report | Portable detailed reports preserving attestation, coverage strata, divergence, survivor and residual data |
| Describe | Explicit file exports; directory/archive/binary paths keep default stdout contracts |
| Binary report | Explicit captured-JSON exports; default existing-report display retained |

The following census targets retain their domain renderers: SCA
specialized fix/check/upgrade/diff/verify/health/bump/triage/fix-diff views; binary
map/investigate/hunt/harness/siblings presentation; CVE diff, threat model,
exploitation evidence reports, evaluation/scorecard/replay, and specialized
precision/dataflow reports. Their structured JSON is supported by the offline
`native` importer, including metadata-only results. Domain-specific presentation
migration remains necessary before claiming full portability for those surfaces.
Help, completion, transport servers, interactive shells, credential/configuration
operations, and acknowledgement-only mutations do not create empty reports.

## Reporting capabilities

`python -m core.reporting capabilities` returns exact integrated command boundaries,
available formats, artifact policies, and summary behavior without analysis or writes.
It does not advertise a whole domain when only its report leaf is integrated.

## SCA offline reports

`sca render findings.json` uses the same portable SCA builder as live scanning.
Its default outputs remain `report.md` and `findings.sarif`, with the common
snapshots and operator summary alongside them. Repeat `--report-format` to select
Markdown, HTML, JSON, or XML; `--report-output` follows the common destination
contract. `--out-md` retains its exact filename semantics, including extensionless
filenames, and conflicts with a separate report destination or non-Markdown format.
`--no-md` keeps SARIF and the quick summary; `--no-report` disables full reports.
`--no-sarif` remains independent. Both legacy skip switches without another report
request retain the existing “nothing to do” exit status.

Regeneration performs no analysis or network queries. Original dependency inventory
coverage, cache statistics, and license metadata remain unknown when unavailable.
Reachability filters affect the presented report and SARIF, while CI thresholds
continue to evaluate the full input. The snapshot records that distinction.
Domain JSON, SARIF, and report destinations must be distinct; reporting/lifecycle
state and immutable generations cannot be used as SARIF outputs.

## Audit and engagement detail reports

Audit's detailed report is built by `core/audit/report_document.py`; engagement's
`build_engagement_document` is a pure builder alongside the existing synthesis
code. They use typed blocks for every section. Domain synthesis, verdict overrides,
attestation checks, journal coverage, and truncation rules remain domain-owned.
Neither rendering nor regeneration performs analysis or promotes a claim.

Default publication includes `audit-report.md` / `engagement-report.md` and their
existing `audit-summary.json` / `engagement-summary.json` portable companions.
The canonical `audit-report.json` / `engagement-report.json` retain their existing
domain schemas. HTML/XML exports use the detailed report stem. Shared filename
overrides keep all formats in one immutable generation while preventing rendered
JSON from replacing domain JSON. An explicit file destination still takes priority
and is checked against protected input artifacts.

`--no-report` retains the minimal summary and canonical data. Explicit format
selection refreshes only requested formats; the engagement CLI announces actual
outputs rather than stale Markdown. Capture failures replace the minimal handoff
with an explicit partial-result diagnostic, while preserving native results and
returning a reporting error.
